# Slepok --- спецификация проекта и техническое задание для MVP

**Название:** Slepok (от русского «слепок», англ. cast / impression).
Команда --- `slepok`, расширение файлов слепков --- `.slepok`.\
**Репозиторий:** https://github.com/miloVV13/slepok (Go-модуль
`github.com/miloVV13/slepok`).\
**Тип документа:** описание продукта, требований и архитектуры.\
**Статус:** живая спецификация; всё, что решено в обсуждении, отражается
здесь. Решения, требующие подтверждения прототипом, перечислены в
разделе 19.\
**Тип проекта:** некоммерческий open source, публикуется на GitHub.\
**Лицензия:** MIT.\
**Язык реализации:** Go.\
**Область:** только проекты для микроконтроллеров (RP2040, затем STM32,
ESP32 и др.). Настольный и серверный софт вне области проекта.

## 1. Идея в одном абзаце

Slepok --- самостоятельная консольная утилита (по модели `git` или
`docker`), которая делает embedded-проект переносимым вместе с его
окружением сборки. Пользователь инициализирует Slepok в каталоге проекта,
работает в любом редакторе, собирает проект через Slepok и, когда проект
собирается, создаёт слепок --- один файл. В слепке находятся исходники,
закреплённые версии SDK, компилятора, build-инструментов и метаданные.
Коллега восстанавливает слепок и собирает проект **без интернета** и без
ручной установки SDK и компилятора.

Slepok не привязан к редактору. Интеграция с редакторами сводится к
стандартным механизмам (`compile_commands.json`, clangd), а не к
плагину конкретной IDE.

## 2. Какую проблему решает продукт

Embedded-проект зависит не только от исходников. Для сборки нужны SDK
производителя, кросс-компилятор, CMake/Ninja, Python и его пакеты,
сторонние библиотеки, переменные окружения и специальные настройки.
Разные версии конфликтуют, устанавливаются разными способами и
усложняют передачу проекта и его сборку через годы.

Slepok делает окружение сборки отдельным, закреплённым, переносимым и
удаляемым объектом.

### Ключевые обещания

-   Один файл содержит проект и всё необходимое для сборки в рамках
    заявленных платформ.
-   После восстановления сборка работает **полностью офлайн**.
-   На принимающей машине не нужно ничего устанавливать, кроме самого
    Slepok (см. 7.3).
-   Зависимости проекта не устанавливаются в систему и не засоряют её.
-   Версии инструментов закреплены, а не скачиваются при каждом запуске.
-   Работоспособность слепка подтверждается реальной проверочной
    сборкой, а не только успешной распаковкой.
-   Slepok работает с любым редактором.

## 3. Главный пользовательский сценарий

```
cd my-project
slepok init --profile rp2040     # создаёт slepok.toml, готовит окружение
# ... пишем код в любом редакторе ...
slepok build                     # сборка в окружении Slepok
slepok shell                     # (опционально) терминал с окружением: cmake, ninja вручную
slepok pack -o abc.slepok          # проверочная сборка + создание слепка
```

На другой машине:

```
slepok unpack abc.slepok ./my-project
cd my-project
slepok build                     # работает без интернета
```

### Правило проверки сборки

Проверкой считается только сборка, выполненная **через Slepok**
(`slepok build` или команды внутри `slepok shell`). Сборка системными
инструментами в обычном терминале не учитывается: Slepok не может знать,
какими версиями она выполнена. Все зависимости проекта добавляются
в окружение через Slepok (профиль, `slepok.toml`), а не установкой в ОС.

## 4. Целевой пользователь и первый профиль

### Основные пользователи

-   разработчики микроконтроллеров (bare-metal C/C++);
-   небольшие команды, передающие проекты друг другу;
-   авторы учебных проектов и лабораторных работ;
-   разработчики, которым нужно архивировать рабочие старые окружения.

### Первый поддерживаемый профиль

-   MCU: Raspberry Pi RP2040;
-   SDK: Pico SDK (со всеми сабмодулями);
-   язык: C/C++, bare metal;
-   сборка: CMake + Ninja (закреплённые версии);
-   компилятор: ARM GNU Toolchain (`arm-none-eabi`);
-   вспомогательные инструменты: готовые бинарники `pioasm` и `picotool`,
    портативный Python (если требуется SDK).

Архитектура позволяет позднее добавлять профили (ESP32/ESP-IDF, STM32,
AVR) без переписывания ядра.

## 5. Границы MVP

### В MVP входит

-   CLI на Go, один бинарник без внешних зависимостей;
-   инициализация проекта с профилем (`slepok.toml`);
-   подготовка окружения из закреплённых пакетов;
-   сборка и интерактивный shell внутри окружения;
-   генерация данных для редакторов (`compile_commands.json` с
    хостовыми путями);
-   упаковка в слепок с обязательной проверочной офлайн-сборкой;
-   проверка архива и контрольных сумм без распаковки и без запуска кода;
-   восстановление и офлайн-сборка на другой машине;
-   понятный отчёт о результате;
-   безопасное поведение при повреждённом архиве и ошибках;
-   локальное управление окружениями, кэшем и местом на диске.

### Не входит в MVP

-   плагин для VS Code или другой IDE (возможен позже как тонкая
    обёртка над CLI);
-   автоматический захват окружения, уже настроенного на хосте;
-   установка произвольных системных пакетов (`apt install` и т. п.);
    допустимы только инструменты, объявленные в профиле или `slepok.toml`
    (см. 7.7);
-   контейнеры (Docker, Podman) и собственная песочница --- не
    планируются (см. 7.3);
-   поддержка всех MCU и SDK;
-   гарантия работы любых программаторов и отладчиков;
-   облачный каталог, аккаунты, синхронизация;
-   побитовая идентичность прошивки;
-   подпись архивов.

## 6. Продуктовые принципы

### 6.1. Инфраструктура скрыта

Пользователь работает с понятиями «проект», «окружение», «слепок»,
«упаковка», «восстановление», «проверка». Ему не нужно знать, как
устроены пакеты и где лежат инструменты.

### 6.2. Слепок самодостаточен

Слепок содержит фактические файлы окружения, а не инструкции «скачай
SDK». Скачивание допустимо только при `init`/подготовке окружения и при
`pack` (если нужных пакетов нет в локальном кэше), но **никогда при
`unpack` и `build`**.

### 6.3. Офлайн доказывается, а не декларируется

`slepok pack` выполняет проверочную сборку в чистом временном каталоге с
отключёнными сетевыми загрузками (см. раздел 10). Если сборка пытается
что-то скачать, упаковка завершается ошибкой.

### 6.4. Изоляция от хоста

Сборка запускается с очищенным окружением: `PATH` содержит только
инструменты окружения и минимальный набор системных утилит, переменные
окружения задаются явно. Случайное использование системного компилятора,
Python или CMake должно быть невозможно.

### 6.5. Не изобретать технологии заново

Slepok не пишет свой компилятор, систему сборки или runtime. Ценность ---
формат слепка, закреплённые профили, проверка, восстановление и UX.

### 6.6. Честно сообщать о гарантиях

Различаются три результата: окружение восстановлено, проект собран,
плата прошита.

## 7. Архитектура

### 7.1. CLI (ядро)

Go-приложение, один статический бинарник. Отвечает за: регистрацию
проектов и окружений; подготовку окружений; сборку и shell; упаковку и
восстановление; чтение и проверку метаданных; контроль целостности;
диагностику; управление кэшем; безопасную обработку ошибок и
незавершённых операций.

### 7.2. Файл проекта `slepok.toml`

Декларативное описание окружения проекта: профиль, версии компонентов,
дополнительные пакеты (например, Python-пакеты), команда сборки,
целевые платформы хоста для упаковки. Окружение всегда воспроизводится
из этого файла; скрытого изменяемого состояния нет.

Минимальный пример (этап 3):

```toml
profile = "rp2040"
board = "pico"
platforms = ["linux-x64"]   # для каких ОС получателя упаковывать пакеты
build_dir = "build"
```

**`slepok.lock`** создаётся `slepok init` и коммитится вместе с
проектом: для каждого компонента --- версия, платформа, URL и sha256
архива производителя (или git-ссылка и коммит) и digest итогового
пакета. Благодаря ему `slepok init` на другой машине (из репозитория,
без слепка) получает побитово то же окружение или явную ошибку.

**Состав проекта в слепке:** все файлы каталога, кроме исключений по
умолчанию (`.git/`, каталог сборки, `*.slepok`, `__pycache__/`,
`.cache/`, временные файлы редакторов) и шаблонов из
`.slepokignore` (синтаксис `.gitignore`). Файлы с признаками секретов
(`.env*`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, `*.p12`, `*.pfx`,
`.netrc`) не упаковываются без явного флага. Решено 2026-10-28.

### 7.3. Бэкенд окружения

Интерфейс, изолирующий способ получения и запуска инструментов.

**Нативный бэкенд (решение принято).** Окружение --- набор закреплённых перемещаемых пакетов
(toolchain, CMake, Ninja, SDK, вспомогательные бинарники, портативный
Python), распакованных в каталог Slepok. Сборка запускается нативно на
хосте с очищенным окружением.

-   Плюсы: на машине получателя не нужно ничего, кроме Slepok; работает
    нативно на Linux, Windows, macOS; редактор видит заголовки по
    реальным путям; быстро.
-   Минусы: окружение ограничено пакетами, которые умеет упаковать Slepok;
    бинарники зависят от ОС хоста, поэтому слепок должен содержать
    пакеты для каждой целевой платформы получателя; изоляция слабее, чем
    в контейнере; поддержка профилей дороже (пакеты под каждую ОС).

**Контейнерный бэкенд не планируется.** Проект ориентирован только на
микроконтроллеры, окружения которых состоят из перемещаемых
инструментов; контейнер добавил бы зависимость от runtime у получателя
и лишил бы нативной работы на Windows/macOS. Интерфейс бэкенда всё же
остаётся отдельным слоем в коде, чтобы ядро не зависело от способа
размещения пакетов.

### 7.4. Профиль платформы

Описывает экосистему MCU: компоненты и их точные версии; источники и
контрольные суммы пакетов для каждой хостовой платформы; лицензии
компонентов; переменные окружения; команды конфигурации и сборки;
критерии успешной проверки; известные ограничения.

Новые MCU подключаются отдельными профилями, а не условиями в ядре.

Профили --- TOML-файлы, встроенные в бинарник (версия профиля
меняется вместе с версией Slepok). Для каждого компонента и платформы
профиль закрепляет источник (URL архива + sha256 или git-URL + тег +
коммит) **и ожидаемый digest итогового пакета**: `init` проверяет обе
суммы. Перед вычислением digest из пакетов удаляются каталоги `.git` и
`__pycache__`. Платформонезависимые компоненты (SDK) имеют платформу
`any`. Переменные окружения и аргументы CMake задаются в профиле
шаблонами вида `{arm-gcc}/bin` (путь пакета в хранилище).

Git-компоненты (Pico SDK с сабмодулями) скачиваются системным `git`;
он нужен только для `init`, не для `build`/`pack`/`unpack`. Решено
2026-10-28.

### 7.5. Локальное хранилище

Каталог Slepok (`$SLEPOK_HOME`, по умолчанию `~/.local/share/slepok`): пакеты окружений, адресуемые по
sha256 (один и тот же toolchain хранится один раз для всех проектов),
временные файлы операций, реестр проектов, учёт занимаемого места.
Экспортируемый слепок обязан содержать всё необходимое независимо от
содержимого локального кэша.

### 7.6. Интеграция с редакторами

Slepok генерирует `compile_commands.json` с хостовыми путями к заголовкам
SDK и toolchain, чтобы clangd и аналогичные инструменты работали в любом
редакторе. Файл содержит абсолютные пути конкретной машины, поэтому
не включается в слепок и генерируется заново на каждой машине (при
`slepok build` после восстановления). Сам `unpack` не запускает CMake
и не генерирует этот файл. Для системных заголовков ARM GCC clangd
может потребоваться разрешение toolchain через `--query-driver`.
Опционально: генерация минимальных проектных настроек для
популярных редакторов, только в проектные файлы и только по команде
пользователя. Личные настройки редактора Slepok не трогает.

### 7.7. Вспомогательные инструменты сборки

Кроме компилятора, CMake и SDK, MCU-проекты часто запускают на хосте
дополнительные программы во время сборки: `protoc` (nanopb), Python со
скриптами и пакетами (генерация шрифтов/изображений, подпись образов),
`git` (версия прошивки), `srecord`, shell-утилиты в скриптах CMake.
В нативном бэкенде каждый такой инструмент должен быть предоставлен
Slepok, иначе сборка упадёт или незаметно использует системную версию.

Механизм --- три уровня, все объявляются в `slepok.toml`:

1.  **Python-пакеты:** список зависимостей с закреплёнными версиями.
    В слепок кладутся wheel-файлы для каждой целевой платформы; при
    восстановлении они устанавливаются в изолированный venv без сети.
2.  **Каталог инструментов:** закреплённые пакеты, описанные в профилях
    (`protoc`, `git`, `srecord` и т. п.), с контрольными суммами для
    каждой ОС.
3.  **Пользовательские инструменты:** путь к перемещаемому архиву или
    каталогу, который включается в слепок как есть и добавляется в
    `PATH`. Ответственность за переносимость --- на пользователе; Slepok
    предупреждает, если инструмент есть не для всех целевых платформ.

Инструменты, не объявленные ни на одном уровне, недоступны в очищенном
`PATH`. Ошибка проявляется при `slepok build` и `slepok pack`, а не на
машине получателя.

Ограничение: проприетарные инструменты, которые нельзя
перераспространять (например, STM32CubeMX, STM32CubeProgrammer), в
профили не входят. Для STM32 слепок содержит уже сгенерированный
CubeMX код, а не сам генератор.

## 8. Состав слепка

### 8.1. Включается

-   исходники проекта и файлы сборки;
-   `slepok.toml`;
-   пакеты окружения для выбранных хостовых платформ;
-   SDK платформы целиком (для RP2040 --- Pico SDK со всеми
    сабмодулями);
-   манифест с версиями, платформами и контрольными суммами;
-   отчёт о проверочной сборке.

### 8.2. Не включается по умолчанию

-   каталоги сборки (`build/` и т. п.): CMake-кэш содержит абсолютные
    пути;
-   секреты: пароли, токены, ключи, сертификаты;
-   личные настройки редактора;
-   история shell, временные файлы, кэш компиляции;
-   `compile_commands.json` и другие файлы с машинно-зависимыми путями;
-   файлы вне каталога проекта;
-   содержимое `.git` (решение по умолчанию; опция включения обсуждается).

Перед упаковкой пользователь видит состав слепка и предупреждения о
потенциально чувствительных файлах. Поддерживается файл исключений
(аналог `.gitignore`).

### 8.3. Переменные окружения

Разделяются на: переменные сборки (из профиля и `slepok.toml`); пути,
вычисляемые Slepok при запуске (например, `PICO_SDK_PATH`); секреты
(никогда не включаются); параметры, передаваемые пользователем при
запуске. Абсолютные пути исходной машины в слепок не попадают.

## 9. Формат слепка

### 9.1. Устройство (формат версии 1)

```
abc.slepok  (поток zstd, внутри tar)
├── manifest.json               # всегда первая запись архива
├── project/<путь>              # файлы проекта
├── packages/<sha256-hex>.tar   # пакеты окружения, по одному tar на пакет
└── reports/verify.json         # результат проверочной сборки (необязателен)
```

### 9.2. Пакет

Пакет --- один компонент окружения (toolchain, CMake, SDK, ...) в виде
**канонического tar**:

-   записи отсортированы по пути (побайтово), каталоги идут перед своим
    содержимым;
-   допустимы каталоги, обычные файлы, симлинки и hardlink-и; hardlink
    допустим только на обычный файл, записанный ранее в том же пакете
    (в ARM GCC 14.2 их 102; замена копиями добавила бы 65 МБ);
-   время изменения, владелец и группа фиксированы (mtime = 0, uid/gid =
    0, без имён); права нормализованы до `0755` (каталоги и
    исполняемые файлы) и `0644` (остальное);
-   формат заголовков PAX, без расширенных атрибутов.

**Digest пакета** --- sha256 от байтов канонического tar. Одинаковое
содержимое всегда даёт одинаковый digest; на этом основаны
дедупликация в локальном хранилище и проверка целостности.

### 9.3. Манифест

JSON, поля (неизвестные поля читатель игнорирует):

-   `formatVersion` --- целое число. Читатель отклоняет слепок с версией
    выше поддерживаемой понятной ошибкой; более старые версии
    поддерживаются;
-   `createdBy` --- версия Slepok, создавшего слепок; `createdAt` --- время
    (UTC);
-   `profile` --- идентификатор и версия профиля;
-   `platforms` --- хостовые платформы, для которых в слепке есть пакеты
    (`linux-x64`, `windows-x64`, ...); пакет с платформой `any`
    (например, SDK из исходников) подходит для всех;
-   `packages` --- список: имя, версия, платформа, digest, размер tar,
    лицензия;
-   `files` --- все файлы проекта и отчёта: путь в архиве, размер,
    sha256, признак исполняемости;
-   `build` --- команда сборки и параметры (заполняется на этапе 3).

### 9.4. Проверка (`validate`)

Потоковое чтение без записи на диск:

1.  первая запись --- `manifest.json`; версия формата поддерживается;
2.  каждая следующая запись описана в манифесте ровно один раз; лишние,
    повторяющиеся и отсутствующие записи --- ошибка;
3.  размер и sha256 каждой записи совпадают с манифестом;
4.  пути безопасны (9.5);
5.  zstd-поток и tar корректно завершены.

Контрольные суммы защищают от повреждения, но не от подмены: тот, кто
изменил архив, может изменить и манифест. Защита от подмены --- подпись
(после MVP).

### 9.5. Безопасность путей

Отклоняются: абсолютные пути, компоненты `..`, пустые компоненты,
обратные слэши, NUL и управляющие символы, устройства, FIFO,
hardlink-и на что-либо, кроме ранее записанного обычного файла того же
пакета, а также симлинки с абсолютной целью или целью вне корня пакета
(проекта). В файлах проекта hardlink-и не допускаются. При распаковке дополнительно проверяется, что ни один путь
не проходит через ранее созданный симлинк.

### 9.6. Распаковка и хранилище

-   Пакеты распаковываются в локальное хранилище
    (`$SLEPOK_HOME`, по умолчанию `~/.local/share/slepok`) в каталог
    `packages/<digest>`; если пакет уже есть, он не распаковывается
    повторно. Каталог пакета появляется только после полной проверки
    (распаковка во временный `packages/.install-*` рядом с окончательным
    каталогом и `rename`: перенос каталога в другой родительский каталог
    требует права записи в сам каталог, которого у read-only пакета
    нет); файлы пакета становятся доступными только для чтения.
-   Права только для чтения защищают от случайной записи, но не
    являются гарантией: процесс, запущенный как root (в том числе root
    внутри user namespace), их обходит. Целостность пакета
    подтверждается только повторным вычислением digest.
-   Проект распаковывается во временный каталог рядом с целевым и
    переименовывается в целевой после проверки всего слепка. Целевой
    каталог не должен существовать.
-   При любой ошибке временные данные удаляются; ничего частичного под
    окончательным именем не остаётся.

### 9.7. Создание

Слепок пишется во временный файл в каталоге назначения, затем
проверяется (`validate`) и только после этого атомарно публикуется под
окончательным именем без перезаписи существующего файла.

### 9.8. Обязательные свойства (сводка)

-   явная версия формата и понятная ошибка при несовместимой версии;
-   манифест читается и проверяется без распаковки всего архива и без
    запуска какого-либо кода из него;
-   контрольные суммы всех файлов и пакетов;
-   защита от path traversal, абсолютных путей и опасных ссылок;
-   атомарное создание: итоговое имя появляется только после успешной
    упаковки и проверки;
-   отсутствие ссылок на внешние изменяемые источники;
-   явный список хостовых платформ, для которых слепок пригоден.

Следует различать размер слепка, размер распакованного окружения и
место, занимаемое общими пакетами в локальном кэше.

## 10. Команды CLI

Реализованный синтаксис Linux MVP:

-   `slepok init [--profile rp2040] [--board pico|pico_w] [dir]` --- инициализировать Slepok в каталоге,
    создать `slepok.toml`, подготовить окружение.
-   `slepok build` --- собрать проект в окружении.
-   `slepok shell` --- открыть shell с окружением.
-   `slepok pack [-o file] [-with-sources] [-allow-sensitive]` --- создать
    слепок; платформы берутся из `slepok.toml`.
-   `slepok unpack <file> [dir]` --- восстановить слепок.
-   `slepok inspect <file>` --- показать содержимое и метаданные слепка.
-   `slepok validate <file>` --- проверить структуру и контрольные суммы.
-   `slepok list` --- проекты и окружения.
-   `slepok gc [-n] [-y]` --- очистка хранилища с предварительным планом.
-   `slepok version` --- версия и доступность сетевой изоляции.

Отдельных `verify` и `remove` нет: чистая проверка входит в `pack`,
исходники пользователь удаляет самостоятельно.

### Поведение команд

**Упаковка:** собрать состав, предупредить о секретах, скопировать
проект во временный каталог, выполнить там чистую проверочную сборку в
офлайн-режиме, создать архив, проверить его, атомарно переименовать.

Офлайн-режим проверочной сборки:

-   `FETCHCONTENT_FULLY_DISCONNECTED=ON` для CMake;
-   запрет загрузки Pico SDK из git (`PICO_SDK_FETCH_FROM_GIT` выключен,
    путь к SDK задан явно);
-   на Linux, где доступно, --- запуск в отдельном сетевом namespace без
    сети средствами Go; при недоступности --- предупреждение, а не ошибка,
    и офлайн-свойство не считается доказанным;
-   проверяются хостовые пути в `CMakeCache.txt` и сгенерированных
    `.ninja`; содержимое произвольных скриптов статически не анализируется.

**Восстановление:** потоково проверить архив, версию формата, платформу
хоста и контрольные суммы, записывая во временные каталоги; готовый
каталог проекта появляется только после полной проверки. Существующий
каталог не перезаписывается. Пакеты размещаются в локальном хранилище;
уже проверенные пакеты могут остаться там при более поздней ошибке.
Затем пользователь запускает `slepok build`, который проверяет
доступность инструментов и создаёт данные для редактора.

**Удаление:** показать, что будет удалено; не удалять пакеты, которые
используют другие проекты; никогда не удалять исходники без явного
подтверждения.

## 11. Хостовые платформы

-   В нативном бэкенде пакеты зависят от ОС и архитектуры хоста. Слепок
    содержит пакеты только для указанных при упаковке платформ;
    восстановление на другой платформе даёт понятную ошибку.
-   Первая поддерживаемая платформа --- Linux x86-64. Затем Windows
    x86-64, затем macOS (arm64/x86-64). Финальная матрица фиксируется
    после прототипа.
-   Сборка не требует подключённой платы.

### Прошивка

Для RP2040 базовый путь --- режим BOOTSEL: плата видна как USB-накопитель,
на который копируется `.uf2`. Это не требует драйверов и работает на
всех ОС. Возможна команда `slepok flash` как удобство. Отсутствие платы не
считается ошибкой окружения. Отладка (SWD/JTAG) в MVP не
гарантируется.

## 12. Безопасность

-   `validate` и `inspect` никогда не запускают код из архива;
-   структура и контрольные суммы проверяются до использования;
-   защита от path traversal, ссылок и записи за пределы целевого
    каталога;
-   секреты исключаются по умолчанию и не выводятся в логи;
-   пользователь явно видит, что сборка слепка запускает build-скрипты
    из его содержимого. В нативном бэкенде они выполняются с правами
    пользователя без изоляции, поэтому слепки из недоверенных источников
    так же опасны, как недоверенный исходный код;
-   контрольная сумма подтверждает целостность, но не авторство.
    Подпись --- после MVP.

## 13. Надёжность и диагностика

### При упаковке

-   исходный проект не изменяется;
-   итоговый файл появляется только после успешной проверки;
-   временные файлы удаляются при ошибке и при прерывании;
-   результат проверочной сборки записывается в слепок.

### При восстановлении

-   проверка архива до распаковки;
-   существующие данные не перезаписываются молча;
-   незавершённое восстановление не помечается успешным;
-   после восстановления проверяется доступность инструментов.

### Отчёт диагностики

Версии Slepok и формата, профиль, хостовая платформа, результат проверки
целостности, обнаруженные версии компонентов, команда сборки и код
завершения, краткое описание ошибки и путь к полному логу.

## 14. Воспроизводимость и гарантии

MVP обеспечивает повторяемую сборку на поддерживаемой платформе с
закреплёнными версиями, но не побитовую идентичность прошивки. Версии
закреплены и проверяются по sha256, плавающих версий (`latest`) нет,
параметры сборки записаны в манифесте, восстановление проверяется
сборкой. Сравнение контрольных сумм прошивок --- после MVP.

## 16. Критерии приёмки MVP

### A --- инициализация и сборка

1.  `slepok init --profile rp2040` в пустом или существующем каталоге.
2.  `slepok build` собирает проект; Pico SDK и ARM GCC в систему не
    устанавливаются.
3.  Логи сборки доступны.
4.  clangd в редакторе видит заголовки SDK через сгенерированный
    `compile_commands.json`.

### B --- упаковка

1.  Собираемый проект упаковывается; проверочная сборка проходит в
    офлайн-режиме.
2.  Проект, которому требуется скачать отсутствующую зависимость при сборке, не
    упаковывается, а пользователь получает понятное сообщение.
3.  В слепок не попадают секреты, `build/` и файлы вне проекта.
4.  Исходный проект не изменяется.

### C --- восстановление на чистой машине без интернета

1.  На машине установлен только Slepok; сеть отключена.
2.  `slepok unpack` + `slepok build` успешно собирают прошивку.

### D --- повреждённый или несовместимый архив

1.  Архив с неверной контрольной суммой отклоняется до распаковки.
2.  Несовместимая версия формата или платформа хоста приводит к
    понятной ошибке.
3.  Незавершённое восстановление не сообщается как успешное;
    существующие проекты не повреждаются.

### E --- плата не подключена

1.  Сборка работает без платы; отсутствие платы не считается ошибкой
    окружения.

### F --- удаление

1.  Удаление проекта не затрагивает другие проекты и общие пакеты,
    которые ещё используются.
2.  Перед удалением показывается перечень данных; очистка кэша не
    удаляет исходники.

## 17. План разработки

### Этап 1 --- прототип без Go

Вручную собрать переносимое окружение RP2040 (toolchain, CMake, Ninja,
SDK с сабмодулями, pioasm/picotool, при необходимости Python), собрать
пример проекта с очищенным окружением без сети, упаковать, распаковать
в другом месте/на другой машине и собрать снова. Измерить размеры.
Проверить, что сборка не требует хостового компилятора и Python.

**Статус: выполнен 2026-10-28 на Linux x86-64** (скрипты в `prototype/`).

Состав окружения: ARM GNU Toolchain 14.2.rel1, CMake 4.3.6, Ninja
1.13.2, Pico SDK 2.3.1 с сабмодулями, pioasm/picotool 2.3.1 (готовые
бинарники pico-sdk-tools), CPython 3.12 (python-build-standalone).

Результаты:

| Показатель | Значение |
|---|---|
| Окружение в распакованном виде (без `.git`) | 1,7 ГБ (из них ARM GCC ~1 ГБ, Pico SDK ~340 МБ, CMake ~200 МБ) |
| Архив окружения + проекта, tar + zstd -19 | 289 МБ |
| Время упаковки (zstd -19, все ядра) | 72 с |
| Время распаковки | 3 с |
| Сборка без сети (`unshare -rn`) и с пустым окружением (`env -i`) | успешно |
| Сборка после переноса окружения в другой каталог | успешно |
| Прошивка (`blink.uf2`) до и после переноса | побитово идентична |
| clangd по сгенерированному `compile_commands.json` | 0 ошибок |

Выводы:

1.  **Очистки `PATH` недостаточно.** Модуль CMake `FindPython` нашёл
    системный `/usr/bin/python3` несмотря на `env -i`: CMake ищет в
    системных префиксах независимо от `PATH`. Обязательно передавать
    `-DCMAKE_FIND_USE_CMAKE_SYSTEM_PATH=OFF` и явные пути к инструментам
    (`Python3_ROOT_DIR`, `PICO_TOOLCHAIN_PATH`, `pioasm_DIR`,
    `picotool_DIR`), а после конфигурации проверять `CMakeCache.txt` и
    `build.ninja` на хостовые пути. Это подтверждает принцип 6.3:
    проверочная сборка нашла утечку, которую декларация бы пропустила.
2.  **Python для RP2040 обязателен:** `boot_stage2` вызывает скрипт
    `pad_checksum` через `find_package(Python3 REQUIRED)`. Портативный
    CPython (~32 МБ в архиве) решает задачу.
3.  **Хостовый компилятор не нужен:** с готовыми pioasm/picotool и
    явными `*_DIR` SDK ничего не собирает для хоста.
4.  **Перемещаемость на Linux не абсолютна:** бинарники зависят от
    системной glibc; pioasm и picotool требуют **glibc ≥ 2.34** (Ubuntu
    22.04+, Debian 12+, Fedora 35+), ninja/pioasm/picotool --- от
    `libstdc++`, picotool --- от `libusb-1.0` и `libudev`. Slepok должен
    проверять эти требования до сборки и записывать их в манифест.
    picotool для сборки не обязателен (только для прошивки/`uf2`
    утилит), поэтому отсутствие `libusb` не должно блокировать сборку.
5.  **clangd:** работает по `compile_commands.json`; с
    `--query-driver=<путь к arm-none-eabi-*>` дополнительно получает
    системные заголовки GCC. Slepok генерирует `.clangd` с этим флагом.
6.  **Сеть при подготовке нестабильна:** загрузки и клонирование
    сабмодулей должны повторяться по частям, с докачкой.

**Статус: основная часть выполнена 2026-10-28** --- команды `init`,

`internal/runner`, `cmd/slepok`. Дополнено 2026-10-28: `list`, `gc`,
README.

Решения по `list` и `gc`:

-   Каждая команда, работающая с проектом (`init`, `build`, `shell`,
    `pack`, `unpack`), записывает его путь в реестр хранилища
    (`projects.json`). Digest пакетов в реестре не хранятся: `gc`
    перечитывает `slepok.lock` живых проектов, lock остаётся
    единственным источником правды. Нечитаемый lock останавливает `gc`.
-   `gc` удаляет пакеты, не нужные ни одному известному проекту,
    загрузки, на которые не ссылается ни один lock, записи о проектах,
    чьих каталогов больше нет, брошенные временные каталоги (старше
    часа) и логи старше 14 дней. Пакеты младше часа не удаляются никогда:
    их может устанавливать параллельный `init`, ещё не записавший lock.
    Перед удалением показывается план; без терминала нужен `-y`.
-   Команды `remove`, удаляющей исходники, нет: удалить проект ---
    значит удалить его каталог, `gc` освобождает место. Slepok не
    стирает код пользователя.
-   Ограничение: проект, перенесённый в другой каталог и ни разу не
    использованный там через Slepok, неизвестен `gc`; его пакеты
    считаются неиспользуемыми. Об этом предупреждает вывод `gc`;
    пакеты возвращаются через `slepok init` (с сетью) или `unpack`.

**Сквозной автотест CLI** (`cmd/slepok/e2e_test.go`, < 1 с, без сети):
весь путь проекта через настоящую функцию `execute` и настоящий код
всех пакетов; подставные только профиль (через `profile.FS`), `cmake`
(маленькая программа на Go из `testdata`) и сервер загрузок (локальный
HTTP), SDK --- локальный git-репозиторий с сабмодулем, закреплённым не
на вершине ветки. Машина A: `init` → `build` → отказ `pack` на `.env`
и на утечке хостового пути → `pack`; подставной `cmake` пытается
подключиться к тестовому серверу, и тест требует, чтобы проверочная
сборка его не достигла. Затем сервер останавливается, машина B (пустое
хранилище): `unpack`, `build` (прошивка совпадает с A), `init` без сети,
`gc`. Мутационная проверка: отключение изоляции в `pack`, проверки
секретов, загрузки сабмодулей или защиты свежих пакетов в `gc` ---
каждое ломает тест.

`execute(args) error`; `slepok version` сообщает, доступна ли на хосте
сетевая изоляция.

Сквозная проверка (Linux x86-64): `slepok init` в пустом каталоге →

Выводы:

1.  **`git submodule update --depth 1` ненадёжен:** он клонирует

Дополнено 2026-10-30: Ctrl+C и SIGTERM отменяют `init`, `build`,
`pack`, `unpack`, `validate` через контекст; CLI возвращает код 130.
Контекст передаётся HTTP-запросам, ожиданиям повторов, git, чтению и
записи архивов, подготовке пакетов и сборке. На Linux дочерние команды
запускаются в отдельной группе процессов, которая завершается при
отмене. Интерактивный `shell` сохраняет обычное поведение сигналов.
Проверенные пакеты и частичные загрузки сохраняются для повторного
использования; временные каталоги операции удаляются. SIGKILL и
отключение питания не позволяют выполнить очистку: старые временные
данные внутри хранилища удаляет `gc`; остатки рядом с целевым архивом
или каталогом проекта могут потребовать ручного удаления.

Добавлены subprocess-тесты SIGINT/SIGTERM во время настоящего `pack`,
проверка завершения потомков процесса, отмена зависшей HTTP-загрузки
и отмена потокового чтения/записи слепка. Проверено отсутствие
незавершённого архива и временной копии проекта после сигнала.

Проверка ENOSPC выполняется на настоящем tmpfs размером 1 МиБ в
изолированных user/mount namespaces: `pack`, `unpack`, установка
пакета, обновление lock и HTTP-загрузка. Частичные результаты не
публикуются, временные данные удаляются, старый lock сохраняется.
Ошибка записи загрузки теперь сразу возвращается пользователю,
без бесполезных сетевых повторов. В CI этот тест обязателен через
`SLEPOK_REQUIRE_FILESYSTEM_TESTS=1`; локально при недоступности
namespaces пропускается. Все эти проверки прошли локально.

Продолжение этапа 4 (2026-10-30): добавлены межпроцессные блокировки
Linux (`flock`). Команды `init`, `build`, `shell`, `pack`, `unpack`,
`list` держат общую блокировку хранилища до завершения операции,
включая запись lock и регистрацию проекта. `gc` держит эксклюзивную
блокировку от чтения реестра до завершения удаления, поэтому не
удаляет данные работающей команды независимо от их возраста.
Загрузка одного checksum и его `.part`, установка одного digest,
обновление реестра и `init` в одном каталоге сериализованы отдельно.
ОС освобождает блокировки при выходе процесса, в том числе SIGKILL;
ожидание блокировки длительной команды отменяется через контекст.
Файлы `.locks/` сохраняются: удаление файла занятой блокировки нарушило
бы взаимное исключение. Поддержка блокировок других ОС относится к
этапу 5. Операции удаления, выполняемые человеком вне Slepok, этими
блокировками не защищены.

Новые проверки: два настоящих процесса CLI одновременно выполняют
`init` разных проектов с общими пакетами; архив скачивается один раз,
оба проекта остаются в реестре, запущенный `gc` ждёт их завершения.
Временные данные в этом тесте искусственно состарены на два часа,
чтобы проверить защиту активной операции независимо от grace period.
Отдельно проверены параллельные обновления реестра и освобождение
блокировки после SIGKILL.

Аварийные сценарии проверены subprocess-тестами: SIGKILL во время
проверочной сборки `pack`, частичной установки пакета и создания
staging при `unpack`. Готовое имя не появляется; после аварии
повторная операция успешна. Старые остатки внутри хранилища удаляет
`gc`, включая `.install-*` и `.projects.json.tmp-*`; остатки рядом с
каталогом проекта остаются для ручного удаления. Это проверяет
аварийное завершение процесса, но не имитирует отключение питания
или потерю данных файловой системой.

Финальная сверка: добавлена проверка литеральных системных путей во
всех сгенерированных `.ninja`, включая `CMakeFiles/rules.ninja`, а не
только в CMake cache. Проверяется отказ `pack` при такой зависимости
и при обязательной загрузке из недоступной сети. `init` существующего
проекта проверен на сохранение исходников и CMakeLists. В CI обязательны
network namespaces и ENOSPC-тест; реальный сценарий дополнен проверкой

### Проверка на живых машинах (2026-10-29)

Первая проверка пользователем на чистой системе выявила три проблемы,
невидимые в разработке (все проверки шли через локальный прокси
пользователя, `HTTPS_PROXY=127.0.0.1:2080`, заданный в окружении
сессии):

1.  **`developer.arm.com` не резолвится** в сети пользователя (тайм-аут
    DNS), тогда как хранилище Arm `armkeil.blob.core.windows.net`, куда
    этот адрес перенаправляет, и GitHub доступны напрямую. Профиль
    теперь качает ARM GCC и его исходники из хранилища Arm, а
    `developer.arm.com` указан зеркалом; файл и sha256 те же. Проверено:
    полный `init` без прокси на пустом хранилище --- 5,7 мин.
2.  **Загрузка не была готова к плохой сети:** не было тайм-аута простоя
    (зависшее соединение вешало `init`), прогресса и зеркал, повторы
    ограничивались 8 попытками независимо от продвижения. Исправлено
    (см. `internal/fetch`): тайм-аут 60 с, прогресс каждые 10 с, повторы
    пока есть продвижение, переход к зеркалу при 403/404/410/451,
    подсказка, как положить файл в кэш вручную.
3.  **Прошивка зависела от даты сборки:** Pico SDK кладёт `__DATE__` в
    binary info, поэтому «побитово одинаковая прошивка» на этапах 1--3
    получалась только при сборке в один день. Теперь `init` записывает
    в `slepok.lock` поле `source_date_epoch` (момент закрепления
    окружения), и сборка экспортирует `SOURCE_DATE_EPOCH`; GCC
    подставляет эту дату в `__DATE__`/`__TIME__`. Заданный пользователем
    `SOURCE_DATE_EPOCH` имеет приоритет. Проверено: дата в прошивке ---
    дата из lock; после `unpack` без сети в пустое хранилище и другой
    каталог прошивка побитово совпадает. Ограничение: смена значения не
    вызывает пересборку уже собранных объектов (инкрементальная сборка);
    проверочная сборка `pack` всегда идёт с нуля.

## 18. Сравнение с существующими решениями

Нужно честно отразить в README:

-   **Nix / Guix pack** --- сильнее в воспроизводимости, но высокий порог
    входа, почти не используются в embedded, нет нативного Windows.
-   **PlatformIO** --- закрепляет версии, но скачивает пакеты из сети;
    офлайн-переносимого файла не даёт.
-   **Dev Containers + `docker save`** --- ручной вариант того же, требует
    Docker и знания его устройства, кросс-ОС только через Linux-VM.
-   **Pico VS Code extension, ESP-IDF installer** --- закреплённые
    инструменты, но привязаны к редактору/экосистеме и без переносимого
    слепка.

Ниша Slepok: один офлайн-файл, доказанное восстановление, без Docker и
без привязки к редактору.

4.  ~~Хостовые инструменты Pico SDK~~ --- решено: готовых

## 20. Главные риски

-   ~~Конфликт имени~~ --- решено. Рабочее название SLPK и расширение
    `.slpk` совпадали с форматом Esri ArcGIS (Scene Layer Package,
    стандарт I3S): ассоциации файлов, поиск и определение типа по
    расширению указывали бы на ГИС. Проект переименован в Slepok,
    расширение --- `.slepok`. Проверено 2026-10-28: имя свободно в npm,
    PyPI, crates.io, AUR и Homebrew; на GitHub есть только небольшой
    неактивный проект `whysafe/slepok` (бэкапы на rsync) из другой
    области. Англоязычным пользователям имя ничего не говорит --- README
    объясняет его в первой строке.
-   **Тонкое ядро:** базовая идея повторяется скриптом в несколько
    десятков строк. Ценность проекта --- в проверке офлайн-сборки,
    профилях, надёжности, интеграции с редакторами и UX. Без них проект
    не нужен.
-   **Утечки хостового окружения** в нативном бэкенде: сборка может
    незаметно использовать системные инструменты (подтверждено
    прототипом: CMake нашёл системный Python при очищенном `PATH`).
    Решение --- очищенное окружение, запрет системных путей поиска
    CMake, проверка сгенерированных файлов сборки на хостовые пути,
    проверочная сборка.
-   **Изменение пакетов хранилища во время сборки:** инструменты
    сборки (Python, кэши) могут писать в каталоги toolchain. Права
    только для чтения защищают лишь от непривилегированного процесса
    (подтверждено на этапе 2 с `unshare -r`). Решение --- изоляция без
    root внутри namespace, отключение записи кэшей и команда проверки
    хранилища (повторный digest).
-   **Системные библиотеки Linux:** бинарники инструментов требуют
    glibc определённой версии (≥ 2.34 для pioasm/picotool) и
    `libstdc++`. Старые дистрибутивы и musl (Alpine) не поддерживаются
    без отдельных пакетов.
-   **Ограничения офлайн-проверки:** надёжное отключение сети есть
    только на Linux и не везде (ограничения user namespaces, например в
    Ubuntu 24.04+). На других ОС проверка опирается на настройки CMake и
    SDK.
-   **Размер слепков**, особенно при нескольких хостовых платформах.
    Решение --- zstd, выбор только нужных платформ, удаление ненужных
    частей toolchain (документация, лишние multilib) там, где это
    безопасно.
-   **Стоимость поддержки профилей:** каждый профиль × каждая ОС.
    Решение --- добавлять по одному, с автоматическими тестами.
-   **Вспомогательные инструменты проекта** (7.7): реальные проекты
    часто используют на хосте что-то кроме toolchain. Если механизм
    объявления инструментов окажется неудобным, пользователи будут
    обходить Slepok. Решение --- хороший каталог, понятные ошибки при
    обращении к необъявленному инструменту.
-   **Лицензии:** обязательства GPL при перераспространении toolchain.

## 21. Определение успеха

> На компьютере A разработчик инициализирует Slepok в RP2040-проекте,
> собирает его и создаёт `abc.slepok`. На компьютере B, где установлен
> только Slepok и **отключён интернет**, разработчик восстанавливает
> слепок и собирает прошивку, а clangd в его редакторе видит заголовки
> SDK.

## 22. Позиционирование

Slepok --- не новый Docker и не менеджер пакетов для одной платы. Это
консольная утилита, которая делает embedded-проекты переносимыми вместе
с окружением сборки: один файл, офлайн-сборка, любой редактор.
