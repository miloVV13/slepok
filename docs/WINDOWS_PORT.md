# Windows x86-64 — этап 5

Статус на 2026-10-30: идёт адаптация ядра. Windows пока не объявлен
поддерживаемым хостом; все Windows-пакеты RP2040 закреплены и проверены
при подготовке, но реальная сборка пока подтверждена только на Linux.
GitHub и нативные проверки через Actions отложены по решению пользователя.

Пошаговая ручная приёмка: [Windows → Windows и Linux ↔ Windows](NATIVE_ACCEPTANCE.md).

## Подготовлено

- Бинарник CLI и тестовые бинарники всех пакетов кросс-компилируются
  для `windows/amd64` официальным Go toolchain.
- Реализована Windows-ветка межпроцессных блокировок через
  [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex):
  общая/эксклюзивная блокировка, неблокирующая попытка и отменяемое
  ожидание. Закрытие файлового дескриптора освобождает блокировку.
  Тест совместного доступа и аварийного завершения процесса перенесён
  в общий набор для Linux и Windows; нативный Windows-запуск ещё нужен.
- `runner.LookPath` на Windows ищет `.exe` внутри окружения и не
  требует Unix execute-bit. Системный `PATH` не используется.
- Перед записью проверяются Windows-имена: drive/ADS-синтаксис с
  двоеточием, устройства, недопустимые символы и окончания точкой/пробелом.
  Политика намеренно выбирает совместимое с Windows 10 подмножество,
  включая отказ для `CON.txt` и аналогичных имён с расширением.
  Основание: [правила имён Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).
- Проверки имён отделены от проверки формата архива. `validate` не
  зависит от хостовой ОС: Linux-архив с `file:stream` допустим для
  проверки целостности, но не для извлечения такого имени на Windows.
  Это касается также целей симлинков. Правила Linux не изменены.
- Для Pico SDK 2.3.1 закреплён отдельный Windows-пакет с представлением
  `windows-v1`. Оно воспроизводится на любой машине подготовки:
  независимые обычные файлы без execute-bit; файловые симлинки заменяются
  копиями целевого содержимого. Git-ссылки определяются по индексу,
  включая сабмодули, и извлекаются с `core.symlinks=false`.
  Привилегии создания симлинков при подготовке/восстановлении такого
  пакета не нужны. Каталожные ссылки, циклы, отсутствующие цели,
  выход за корень, Windows-устройства и конфликты регистра отклоняются.
- В `slepok.lock` сохраняется выбранный `source.layout`. Пакет хостовой
  платформы имеет приоритет над `any` с тем же именем независимо от
  порядка записей. `unpack` проверяет все пакеты, но извлекает только
  выбранный вариант — Linux SDK не устанавливается на Windows рядом
  с его Windows-заменой.
- Закреплены остальные шесть Windows-компонентов: ARM GCC, CMake,
  Ninja, Python и SDK tools. Проверены архивные checksum, экспортный
  digest, ожидаемые пути и PE AMD64. Добавлены настройки Windows в
  профиле, дополнение lock при добавлении платформы и проверка полноты
  пакетов перед `pack`. Подробности: [Windows packages](WINDOWS_PACKAGES.md).

Дополнительных Go-модулей не добавлено. `LockFileEx` вызывается через
стандартный `syscall`; DLL `kernel32.dll` относится к Windows KnownDLLs.

## Обнаруженные задачи до включения Windows-профиля

1. **Windows-представление SDK и восстановление.** Windows
   [не сохраняет Unix-права через `os.Chmod`](https://pkg.go.dev/os#Chmod).
   В SDK найдены 328 исполняемых файлов и 2 ссылки на документы TinyUSB.
   Выбрано разделение представлений: исходный `any` для Linux остаётся
   прежним, Windows получает `windows-v1`. Новый digest проверен на
   полной копии SDK, после распаковки и имитации Windows-прав;
   первая нативная подготовка пользователя также прошла без ошибки
   digest. Остаётся проверить восстановление на чистом получателе.
   Формат канонического tar и
   существующие Linux digest не изменены. В слепок для двух ОС входят
   оба SDK, что увеличивает размер, но не требует служебных метаданных
   хранилища и привилегий на симлинки.
2. **Нативный запуск пакетов RP2040.** Каталог из семи пакетов закреплён,
   структура и настройки запуска проверены. Следующий шаг — выполнить
   `init`, `build`, `pack`, `unpack`, повторный `build` на Windows и
   проверить DLL-зависимости в чистой системе.
3. **Нативные файловые операции.** Проверить read-only деревья,
   атомарную публикацию, обновление реестра при открытом читателе,
   регистр имён, длинные пути, симлинки и права на их создание.
4. **Процессы и shell.** Реализованы Windows PowerShell без профиля,
   временный `cmake.exe`, передающий аргументы без интерполяции в скрипт,
   и Job Object для отмены дерева инструментов. Супервизор входит в job
   до запуска инструмента; при отмене закрывается его единственный job
   handle. Добавлены нативные тесты кодов возврата и отмены потомка.
   Выполнение этих тестов и проверка Ctrl+C в настоящем PowerShell
   ещё предстоят, как и проверка окружения на Windows-инструментах.
5. **Офлайн-проверка.** Механизм Linux namespaces недоступен. До
   появления проверенного механизма сеть считается неизолированной;
   такой запуск не выдавать за доказанную офлайн-сборку.
6. **Приёмка.** Windows → Windows на чистой машине без сети; затем
   слепок с пакетами для Linux и Windows. Проверить весь CLI, IDE и
   аварийные/параллельные сценарии. Кросс-сборка этого не заменяет.
   Мультиплатформенная подготовка теперь реализована на обеих ОС:
   чужие пакеты сохраняются в канонических tar без извлечения.
   Дополнительно проверить Windows → Linux и переупаковку общего
   слепка на Windows без сети, как описано в инструкции приёмки.

## Сохранение Unix-метаданных на Windows

`init` на Windows готовит Linux-пакеты через логическое дерево:
содержимое пишется во временные файлы с непрозрачными именами,
а Unix-пути, права и типы ссылок хранятся отдельно в памяти.
Vendor tar/zip поставляет метаданные напрямую; для Git используются
режимы `100644`, `100755`, `120000` из индекса, включая сабмодули.
Git извлекает ссылки как обычные файлы-заглушки. Канонический tar
собирается в прежнем порядке и с прежними заголовками.

Хранилище различает исполняемое дерево `packages/<hex>` и архив
`archives/<hex>`. `build` требует именно дерево текущей ОС;
`pack` умеет читать обе формы и сверяет digest с lock. Чужие пакеты
при `unpack` проверяются и сохраняются архивами, поэтому общий
слепок можно переупаковать на другой ОС без скачиваний. Архивы
учитываются в `list`, реестре ссылок и `gc`; публикация защищена
той же пакетной блокировкой, что и установка дерева.

На Linux проверен переносимый путь для всех шести настоящих vendor
архивов и полного SDK: все семь прежних Linux digest совпали.
SDK проверен с заглушками симлинков и без Unix execute-bit, права
восстановлены из индекса Git. Отдельный тест проверяет цепочку
`pack → Windows-unpack → repack → Linux-unpack`, включая режим
исполнения, symlink, hardlink и неизменный digest. Этот тест выполняет
логику выбора платформы на Linux; нативный запуск Windows ещё нужен.

Повторение проверок без сети с уже имеющимися архивами/SDK:

```sh
SLEPOK_LINUX_ARCHIVES=/absolute/path/to/vendor-archives \
  go test -v ./internal/fetch -run '^TestRealPortableArchives$' -count=1
SLEPOK_PORTABLE_SDK_SOURCE=/absolute/path/to/pico-sdk \
  go test -v ./internal/fetch -run '^TestRealPortableSDK$' -count=1
```

Первый тест ожидает имена файлов из `portable_test.go` и проверяет
vendor SHA256 до обработки. Второй работает с приватной копией SDK.
Подготовка больших пакетов временно требует места и для содержимого,
и для канонического tar; ARM GCC tar занимает около 1 ГБ.

## Проверка SDK на реальных данных

`TestRealWindowsSDK` работает с временной копией исходного SDK и сначала
проверяет исходный Linux digest по профилю, затем преобразует дерево,
упаковывает, распаковывает и повторно проверяет digest после изменения
прав на аналогичные Windows. Локальная проверка 2026-10-30 пройдена:

| Представление | SHA256 канонического пакета |
|---|---|
| Linux / `any`, сохранён прежним | `b6f7eccbf2159b28801e0ffee13ba178656d5f649f5b280fe3420a0c66f2e92c` |
| `windows-v1` | `b703458527aae69f96c8ad1b162d4bc8d019641bd6eaa150a954a076c83271c2` |

Windows tar: 337 903 616 байт. Отдельные тесты проверяют равенство
пакетов из Unix-ссылок и Windows-файлов-заглушек, Git-сабмодули,
безопасность графа ссылок, конфликты регистра и выбор вариантов при
восстановлении мультиплатформенного слепка. Путь подготовки сабмодуля
также ограничен корнем репозитория: `..` и ссылка родителя наружу
не могут привести к удалению внешних файлов.

```sh
SLEPOK_WINDOWS_SDK_SOURCE=/absolute/path/to/pico-sdk \
  go test -v ./internal/fetch -run TestRealWindowsSDK -count=1
```

## Проверка с Linux

Обычная полная установка Go содержит Windows-часть стандартной
библиотеки. Go в текущей системе её не содержал; для проверки использован
официальный `go1.27.3` через разовую переменную `GOTOOLCHAIN`, без
изменения системных настроек Go или минимальной версии в `go.mod`.

```sh
GOTOOLCHAIN=go1.27.3 GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
  go build -o /tmp/slepok-windows.exe ./cmd/slepok
mkdir -p /tmp/slepok-windows-tests
GOTOOLCHAIN=go1.27.3 GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
  go test -c -o /tmp/slepok-windows-tests ./...
GOTOOLCHAIN=go1.27.3 GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go vet ./...
```

На Windows сначала выполнить `go test ./internal/process ./internal/filelock ./internal/safepath`
и `go test ./internal/runner`. Полный существующий набор пока содержит
проверки, предполагающие Unix-права и доступность симлинков; его нельзя
считать пройденным только по успешной компиляции.

## Использование без настройки окружения

Первая нативная проверка пользователя подтвердила подготовку всех 14
пакетов Linux/Windows и успешную конфигурацию CMake на Windows.
Сборка остановилась на вложенном `cmd.exe`: очищенный PATH не содержал
System32. Исправлено добавлением `%SystemRoot%\System32` после путей
закреплённых инструментов и явным `ComSpec`. Пользовательский PATH
по-прежнему не наследуется. Добавлен Windows-тест вложенного вызова
`cmd.exe` в окружении сборки; здесь он только кросс-компилирован.
Повторный нативный `build` прошёл: получены UF2, ELF, BIN и HEX.
Следующий `pack` выполнил проверочную сборку, но обнаружил системный
`cmd.exe` как внешнюю зависимость. Проверка исправлена точечным
исключением `%SystemRoot%\System32\cmd.exe` в CMake cache и Ninja;
весь каталог System32 не разрешается. Сторонние Python/компиляторы,
похожие имена и `cmd.exe` из другого каталога по-прежнему отклоняются.
Повторный нативный `pack` и перенос ещё предстоят.

`SLEPOK_HOME` не обязательна. По умолчанию хранилище создаётся в
`%LOCALAPPDATA%\slepok`; если `LOCALAPPDATA` отсутствует, используется
`AppData\Local\slepok` внутри домашнего каталога. Относительный путь
явного override преобразуется в абсолютный при открытии хранилища.
Переменная в тестовых инструкциях лишь позволяет имитировать две
машины с разными пустыми хранилищами.

Получателю достаточно `slepok.exe` и слепка с пакетами `windows-x64`:

```powershell
.\slepok.exe unpack .\blink.slepok .\restored
cd .\restored
..\slepok.exe build
```

Команды предполагают, что бинарник и архив лежат в исходном каталоге.
Не требуются изменение PATH, установка SDK, Go или Git и разрешение
PowerShell-скриптов. `slepok shell` сам выбирает встроенный Windows
PowerShell и добавляет инструменты только в окружение открытого shell.
Для обычных `unpack` и `build` запуск shell не нужен.

Нативная приёмка остаётся обязательной: на подготовленной Windows
выполнить `init`, `build`, `pack`, затем перенести архив и бинарник
на чистую Windows, отключить сеть и выполнить команды выше. Сравнить
UF2 для одинаковых исходников и lock; проверить пути в новом
`build/compile_commands.json`. Windows-сборка без отключения сети
пока не доказывает автономность: сетевой изоляции на Windows нет.
